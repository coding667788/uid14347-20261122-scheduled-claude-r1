为虚构的内部认证系统交付两段挑战账本。请求被登记在账户、资源域和操作版本下；首阶段要完成设备因子和人工因子，两个因子由不同主体提供，完成后记录预授权，低风险版本在同一事务重新核对绑定并签发。高风险版本需要第二阶段的新确认，不能把首阶段已消费证明再次使用。每个证明绑定挑战编号、阶段、因子类型和账户身份世代，有明确截止。组织可在两阶段之间迁移账户，新身份世代只允许收到与当前版本对齐的证明；迁移记录可以显式保留已完成首阶段，但仅当旧新资源域、操作版本及风险级别都一致，并要求在同一事务消费迁移令牌。令牌绑定具体挑战及旧新世代。
advance 将证明验证、状态迁移和唯一签发回执写在同一 SQLite 事务；签发时再检查资源版本、显式撤销和当前世代。apply 也可登记迁移、升级风险或撤销因子。重复事件返回原结果，冲突拒绝整批。explain 对任一历史提交号列出状态和失败因子，不把后追加的撤销追溯到已签回执。验证新世代注入旧阶段凭证失败、迁移和签发竞争、首阶段保留但第二阶段必须重做、同一证明并发消费、同 ID 异内容、响应前进程退出。所有证明仅用合成 ID 和布尔可信标记。

迁移改为可链式转移：同一账户可能在第一次确认后连续跨组织多次。每一步必须独立消费属于当前挑战的迁移令牌，且绑定该步的资源、前序迁移回执摘要和验证政策版本；任何令牌不能直接跨过一个世代，即使把资源转回原组织。政策可给同阶段若干可替代证明配方，每个配方列所需因子以及不同主体、不同信任组的条件。在步骤后重新裁定所有仍有效、未撤销且绑定该阶段的证明，选择最少消耗、再按证明 ID 最小的一组；被保留的首阶段只保留已消费事实，不自动使它满足后来更严的配方。第二阶段可在同一批先遇政策升档或关键证据失效，必须回到首次未满足阶段并记录前一阶段回执失效原因，但保留所有旧消耗不可再用。加入完全持久化的 SQLite 多进程协调与测试：同批乱序迁移票的前序约束、实际组三选二与单因子分别都合格但组合不独立、重回原组织旧票仍拒绝、回退首阶段后发生批次重入、历史查询与当前撤回分开，以及本轮部分消费后提交失败。用有限状态对照核对随机小案。

请为挑战、证明消费和迁移提供可直接运行的本地虚构案例。空仓库中的实现须能在 Windows 原生 Python 3.12 上以标准库和 CPU 运行。用 `python -m solution <命令> CASE.json` 提交案例，持久账本相关命令加 `--db DB.sqlite`。相同逻辑输入必须得到一致的结果，统一以 UTF-8 JSON 写到 stdout。结构错误同时给可定位的错误码和字段位置。README 写全输入输出定义与复现命令，执行 `python -m unittest discover -s tests -v` 即可运行配套断言测试。
